Usage guide

One working theory. Three ways to keep it useful.

Augmented Workflow gives product, design, and engineering a shared place to leave intent, judgment, and evidence. Each discipline contributes a different kind of clarity; none needs to become the owner of everyone else’s work.

Use the same loop, at the right depth.

Not every change needs a full process. Leave enough context for the next person or agent to understand what matters, make a justified change, and show what was checked.

A universal first move

Ask aw-help what belongs next.

When the team has a concrete question but is unsure which workflow step fits, start with a plain-language prompt.

  • “We need to explore a new onboarding problem.”
  • “This spec is ready for implementation.”
  • “A reviewer found a bug in this PR.”
What it returns

One clear next step, grounded in the repo.

aw-help reads the current workflow configuration and points to the appropriate skill—such as brainstorming, spec creation, planning, implementation, review, or PR feedback—without asking the team to memorize the system.

Product: name what must be true.

Product owns the outcome and boundaries. The goal is a clear account of the problem that lets design and engineering make informed choices without turning every detail into a ticket.

Product contribution

Keep current intent current.

Use a brainstorm, PRD, or living spec to distinguish the user problem from a proposed solution. Update it when learning changes the product’s direction.

Start

Frame the decision

  • Who is affected?
  • What changes for them?
  • What is out of scope?
Contribute

Make tradeoffs legible

  • Write acceptance examples
  • Link prior decisions
  • Keep open questions visible
Hand off

Review the outcome

  • Check shipped behavior
  • Update intent when it moved
  • Capture consequential choices

Design: make the experience concrete.

Design turns product intent into a usable path through the interface. Its contribution is the reasoning about states, language, behavior, and what a person needs at each moment.

Design contribution

Keep experience decisions close to the work.

Use design hooks and reference material when they help. Put durable interaction requirements in the feature spec, and preserve consequential tradeoffs where later contributors can find them.

Start

Interrogate the flow

  • Map the primary path
  • Name empty, error, and loading states
  • Check accessibility and content needs
Contribute

Record the why

  • Clarify interaction requirements
  • Link design references
  • Surface experience risks
Hand off

Inspect the result

  • Review the implemented flow
  • Check responsive edge states
  • Turn useful corrections into guidance

Engineering: make change explainable.

Engineering connects intent to the running system. Read the current spec, decisions, standards, and prior lessons before choosing an approach; return a result that another engineer or agent can inspect and extend.

Engineering contribution

Change the system with a basis.

Use the smallest workflow that fits the risk. A tiny correction may need only a focused check; a cross-cutting behavior change needs explicit acceptance coverage and review evidence.

Start

Load relevant context

  • Read the spec and decisions
  • Apply project standards
  • Name assumptions before coding
Contribute

Prove the change

  • Map criteria to checks
  • Keep traceability near behavior
  • Leave limits visible
Hand off

Make review possible

  • Summarize behavior and checks
  • Update specs when behavior changed
  • Capture durable lessons

Use aw-gate.js to make evidence visible.

The gate is the deterministic boundary of the workflow. It checks whether a repository contains the evidence a team expects, without pretending it can judge the quality of a product decision or design.

Validate

Check the artifact structure.

Run node .scripts/aw-gate.js validate after changing durable docs. It catches missing or unindexed feature artifacts and invalid learning references before they become stale context.

Record

Leave proof when work is done.

Review and compliance steps write receipts and freshness records after they complete. Those records let a later contributor see which checks ran and when.

Enforce

Require fresh evidence.

Wire node .scripts/aw-gate.js check into a pre-push hook or CI job when the team is ready to require fresh review and compliance evidence before delivery.

Interpret

Keep judgment with people.

Passing validate or check shows that expected evidence is present and current. Product, design, and engineering still decide whether it is relevant, sufficient, and responsible.

Three examples, from one team.

These are small, concrete uses of the shared loop. The point is not to create more ceremony; it is to leave the next contributor a useful basis for action.

Product example

A vague request becomes a spec.

Product uses aw-help, then a brainstorm to define who needs a notification, when it appears, and which edge cases matter. The result is a living spec with acceptance examples.

Design example

A flow gains its missing states.

Design reviews the spec, records empty, error, and accessibility requirements, and links the interaction decisions that engineering should preserve.

Engineering example

An implementation returns evidence.

Engineering maps the acceptance criteria to checks, ships the smallest justified change, and captures a learning when a correction should guide future work.

A simple first week

Begin with one meaningful feature.

Start with a practice that makes a future decision easier.

  • Write or refresh one living spec
  • Record one decision worth reusing
  • Run one review and capture one correction
Keep the burden proportional

Use only the evidence the next change needs.

Augmented Workflow is useful when it reduces reconstruction work. If an artifact cannot help someone make a better future decision, keep it lightweight or do not create it.

Teams can configure explicit design checkpoints in docs/workflow/config.yml.

Shared responsibility

Leave the next contributor a clearer starting point.

Product, design, and engineering do different work. Augmented Workflow helps them leave compatible evidence so people and agents can carry that work forward with judgment.
